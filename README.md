# FDE 交付知识库

## 标准目录结构

每个项目目录内部按交付生命周期组织，与复盘会的五段式理念同源——先看输入，再做调研，交付落地，运营验证，最后沉淀复用：

```
<项目代号>/
├── README.md      # 项目一页纸：客户 / 命题 / 周期 / 交付物索引 / 当前待办
├── 01-输入/       # 原始资料，只进不改：访谈转写、会议纪要、客户文档、素材图片
├── 02-调研/       # 中间产出：SOP 摸查、链路梳理、需求分析
├── 03-交付/       # 对外正式交付物，版本化命名：SOP、说明书、汇总表
├── 04-运营/       # 落地后的持续动作：复盘台账、周会记录、工作汇报
├── 05-沉淀/       # 跨项目可复用的模板与方法论
└── _work/         # 脚本与中间产物（可随时重建的东西不算资产）
```

四条原则：

1. **原始输入只进不改**——访谈转写、微信截图、客户发来的文档是证据链，保留原样，调研结论的每一条都能追溯到输入；
2. **交付物版本化**——命名 `名称-版本-YYYYMMDD`，正式对外文档 md + pdf（或 html）双格式，改版不改旧文件；
3. **中间产物不污染交付目录**——生成脚本、`_` 前缀的中间文件、图片切片一律进 `_work/`；
4. **能复用的才是沉淀**——`05-沉淀/` 里的模板（如五段式复盘模板、需求分析样板）比单个项目的交付物更值钱，成熟后可提升到顶层复用。

## 新项目开张三步

1. 复制 `_template/` 为新目录，代号用小写短词（如 `golo`），目录内改日期和占位内容；
2. 填写项目 README 一页纸（客户、命题、对接人、周期）；
3. 在本文件「项目索引」表加一行。

## FDE 方法论笔记（岗位指南）

1、FDE 服务形成的业务闭环最值钱，前提是那个闭环跑在我们的系统上，客户停付费闭环就断。如果闭环只是"你帮他们理顺了流程"，他们自己就能跑，那不算你的。

2、AI 组织是反馈闭环的快速迭代能力，我们应该强调各场景下的完整闭环，比如从市场分析-人群分析-产品选择-价格带制定-内容策略-内容生产-上架-投流-下架 这样的完整业务闭环；或者人事从人才画像定义-招聘-考勤-绩效-工资管理-离职；供应链...；或者在有"市场分析-人群分析-产品选择-价格带制定-内容策略-内容生产-上架-投流-下架"后，我们再描述细化的内容生产比如 muse ai、scriptforge 等业务闭环。

> **AI 时代的组织能力：用反馈迭代替代严格执行：**
> 1、传统公司靠人工复盘调整，未来公司通过数据+智能体+质量反馈机制自动循环：
> 发现问题->分析原因->补工具/改规则->持续优化。
> 2、未来公司的竞争"不是人多"，而是"闭环多"，增长闭环、销售闭环、客服闭环、研发闭环、内容闭环、运营闭环......
> 每个闭环具备感知->决策->执行->评估->学习能力。
> 3、企业级上下文（客户理解/业务规则/历史决策/产品路线图）成为新基建。
> 当业务逻辑散落在人脑和文档中，AI 无法真正接管工作。
> 4、要按照 AI 可读的方式来建公司，所有业务工作都要被记录，所有关键知识都要被结构化，所有流程都能够被智能体调用，所有失败都要能反馈，所有经验都要能沉淀。
